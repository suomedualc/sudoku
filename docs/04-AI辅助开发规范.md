## 1. 四层上下文在本项目的落地

| 层级 | 本项目载体 | 用途 | 优先级 | 当前状态 |
|---|---|---|---|---|
| 系统层 | `.codebuddy/rules/sudoku-dev.md` | 全局开发纪律（分层、红线、选型约束） | 自动加载 | ✅ 已落地（v1.1 起含开发思路与选型依据） |
| 项目层 | `docs/01`–`docs/05` | 团队 / 跨会话共享的架构、规范、流程、规划 | 中 | ✅ 5 本，索引见 §0 |
| 对话层 | `@file` `@folder` `@code` `@terminal` 主动注入 | 当前任务的精准信息，可覆盖任何层级 | 最高 | 按需注入 |
| 会话层 | 当前对话（含 TODO 列表） | 本次任务的临时状态与推进记录 | 临时 | 任务结束即丢，值得留存的结论要回写文档 |

**约定**：每个新功能开发前，先 `@folder composeApp/src` 做一次"预热"，让 AI 认识结构；
再针对单文件用 `@file` / `@code` 精准注入，**避免一次性把整个工程塞进上下文**。

## 2. 金发姑娘原则：给 AI 的"刚刚好"信息

- **太少**：不说明"这是 Compose Multiplatform + miuix"就直接要改 UI → AI 用错组件库（如改用 Material3）。
- **太多**：把 200 行的 `Sudoku.kt` 整段粘贴只为改一个函数 → 噪声压垮重点。
- **正好**：`@code` 只引 50–100 行目标函数 + 一句话需求 + 负面约束（见 §6）。
- **够而不越**：涉及跨层改动（如"加一个玩法开关"）时，按 §4 的流水线逐层投喂，而不是一次给三层。

## 3. @ 引用使用约定

| 场景 | 写法 | 说明 |
|---|---|---|
| 改某文件 | `@file composeApp/src/commonMain/kotlin/org/example/sudoku/state/GameReducer.kt` | 注入完整文件 |
| 改某段逻辑 | `@code` 选中 50–100 行 | 避免注入整文件被截断 |
| 排错 | `@terminal` + `@file 出错文件` | 同时看真实报错与源码 |
| 了解结构 | `@folder composeApp/src/commonMain` | 只看结构不阅内容 |
| 查 miuix API | `@docs <miuix 官方页>` 或直接反查本地 jar | 依签名生成代码；本仓已实测过 0.9.2 的签名（见 `docs/03` §2） |

> `@` 必须手动输入触发；粘贴文本中的 `@` 不生效。`@terminal` 取的是内置终端**最近一次**真实输出。

## 4. 分层投喂流水线（与 core / state / ui 分层天然对齐）

复杂功能按"类型优先、逐层依赖"拆解，**每一步只引用上一步产物**，杜绝跨层大杂烩：

```
需求文档/Issue  →  ① 类型定义(core/state 的 data class)
                 → ② 状态动作(GameAction) + 归约(GameReducer)
                 → ③ 存储/平台封装(entrypoints 或 expect/actual)
                 → ④ UI 组件(ui/components) + 屏幕(ui/screens)
                 → ⑤ 组装(App.kt / 导航 / 主题)
```

- 类型文件优先于实现文件：`core/Sudoku.kt`、`state/GameState.kt` 是真相源，先定它们。
- 每层用**新建对话**递进引用，错误在上一层对话修正，不跨层污染。
- 本仓现有结构的"锚点"（新会话可直接引用）：

```
core   : core/Sudoku.kt（Board/Game/Solver/出题/冲突/合法掩码/时长格式化）
state  : state/GameState.kt · GameAction.kt · GameReducer.kt · GameViewModel.kt · GameStore.kt
ui     : ui/App.kt · ui/theme/{Ink,DesignTokens}.kt
         ui/components/{BoardCanvas,NumberPad,FloatingPad,TopDrawer,InkWidgets}.kt
         ui/screens/{Menu,Game}Screen.kt
test   : commonTest 59 项（内核 5 + 状态机 13 + 计时 5 + 存档 10 + 悬浮面板 7 + 抽屉仲裁 9 + 格子语义文案 7 + 动效策略 3）
         jvmTest 11 项（TopDrawerUiTest 4 键盘路由 + BoardCanvasUiTest 4 格子语义与点击穿透 + BundledFontsTest 3 字体资源）
```

## 5. 四种污染与规避

| 污染 | 本项目的典型表现 | 规避手段 |
|---|---|---|
| 陈旧信息 | 引用归档前的 TS / Rust 实现，或引用已删除的 `tools/shot.py` | 旧实现只在 `archive/`；以 `docs/01`–`05` + 当前 Kotlin 源码为准 |
| 噪声过多 | 整工程粘贴 | 用 `@code` 只引相关片段 |
| 矛盾信息 | 同一对话混谈 Android 与桌面两套构建 | **一个任务一个对话**；跨目标改动拆开 |
| 跨任务污染 | 一个对话同时谈"出题算法"与"Snackbar 样式" | 严格单任务；新任务开头设锚点（见 §7） |

## 6. 负面上下文（禁止项清单）

以下是红线摘要，**完整版与解释见 `.codebuddy/rules/sudoku-dev.md`**：

- 不修改 `core/` 领域算法而不补 `commonTest` 单测；
- 不给 `state/` 引入 Compose / 平台 API（保持纯状态机、可回放）；
- 不新增第三方依赖（含升级 miuix）而不先在 `gradle/libs.versions.toml` 对齐版本并登记理由；
- 不改变 `state` 对外类型 / Action 而不同步更新 `docs/01-架构设计.md`；
- 不在无网络环境尝试**首次** `gradle build`（会卡在依赖下载）——先声明约束再规划；
- 不把 `archive/` 里的 TS / Rust 旧实现当作当前实现引用；
- 不在 `DesignTokens` 里硬编码颜色（一律走 `MiuixTheme.colorScheme` 语义色）；
- 文档与代码必须同一次改动内保持一致，不留"下次再改文档"。

## 7. 预热与锚点模板

**预热（新会话开头）**

```
@folder composeApp/src/commonMain
这是 Kotlin + Compose Multiplatform + miuix 的数独项目（当前只启用 Desktop/JVM 目标）。
分层：core 纯算法 / state 纯状态机 / ui 表现层。规则见 .codebuddy/rules/sudoku-dev.md。
请确认你已理解结构再开始。
```

**锚点（对话变长或切换任务时）**

```
锚点：
  core  = core/Sudoku.kt（位掩码 + MRV 求解 / 唯一解挖洞 / 冲突 / legalMask）
  state = GameState · GameAction · GameReducer（纯 reduce）· GameViewModel
  ui    = BoardCanvas（自绘 Canvas）· NumberPad · FloatingPad · TopDrawer · Menu/GameScreen · App.kt
  测试  = 70 项（SudokuTest 5 + GameReducerTest 13 + 存档 10 + 格子语义 11 + 动效策略 3 + UI 8），运行 .\gradlew.bat :composeApp:jvmTest --offline
  环境  = JAVA_HOME 必须是 JDK 21（JDK 25 会直接失败）
现在新任务：[功能描述]。约束见 rules/sudoku-dev.md。
```

## 8. 急救

AI 输出混乱时：① 缩减上下文只留 1 个最关键 `@`；② 重开对话；③ 一句话重述目标 + 负面约束（§6）；
④ 若涉及版本 / 构建报错，先把 `@terminal` 的真实报错贴上，再谈方案。

## 9. 维护约定

- **文档随代码走**：改行为 → 同一次改动内更新对应文档（映射关系见 §0 表）。
- **新增文档**：必须在 `README.md` 的"文档索引"与本文 §0 表登记，否则视为孤儿文档。
- **重大变更后复核**：新增平台 / 依赖升级 / `state` 接口变更 → 复核 `docs/01`、`docs/02`、`docs/03`、`docs/05`
  四本里的相关章节（历史上出现过"文档写了窗口尺寸与键盘映射、代码里没有"的偏差）。
