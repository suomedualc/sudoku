## 1. 架构与分层（精读结论）

```
core/          Sudoku（位掩码 + MRV 回溯求解/出题）· CellCursor（光标纯逻辑）
                 ↑ 零平台依赖、零 UI、零 IO
state/         GameAction → GameReducer.reduce() → Reduction(state, Msg)
               GameState（不可变快照）· GameStore/SaveCodec（v2 文本存档）
               GameViewModel（唯一桥：动作分发 / 事件通道 / 单调时钟 / 落盘）
                 ↑ 零平台依赖（存档走"端口+注入"而非 expect/actual）
ui/            theme（Ink 纸墨令牌 · DesignTokens 尺寸动效）
               components（全自绘：BoardCanvas / InkWidgets / TopDrawer / NumberPad / FloatingPad）
               screens（MenuScreen / GameScreen）· i18n（Strings 接口 + 中英双字典）
                 ↑ 仅通过 7 个 expect/actual 触达平台
platform/      androidMain / jvmMain：GameStore 实现 · SaveMutex · 字体 · 安全区 · 返回键 · 语言
```

**做对的关键决策**（值得保留，不要在重构时"优化"掉）：

1. **提示是事件不是状态**（`Reduction.message` + `Channel`）：绕开了"相同文案被等值比较吞掉"这个经典坑。
2. **存档走端口注入而非 expect/actual**：`state/` 保持零平台依赖，测试可注入内存实现。
3. **计时用单调时钟 + 锚点并账**，而非"每秒 +1"：长局不漂移，切后台/最小化能精确停表。
4. **`derivedStateOf` 缓存 conflicts/progress**：心跳 250ms 不触发 81 格重算。
5. **视觉只有纸墨两色 + 墨四级 alpha**：无障碍对比度可量算（`Ink` 里直接写了实测值 17.40:1 等）。
6. **键位兜底三条硬规则**（方向键/退格/Delete 永不受键位设置影响）：防止玩家把自己锁在门外。

**架构层面唯一实质建议**：`GameViewModel` 承担了过多职责（动作分发 + 事件通道 + 计时 + 落盘 + 派生缓存），且 `dispatch` 是同步执行——目前因出题实测 <20ms 尚可接受，但一旦引入"暂停菜单里出题动画"或"网络题库"就必须拆。详见 §4。

## 2. 缺陷清单（按严重度）

### P1-A · Android 旋转/重建后存档静默降级为只读 —— 已实测复现

**位置**：`androidMain/MainActivity.kt`（`remember { MutexGameStore(...) }`）+ `MutexGameStore`（`GameStore.kt:95`）

**问题链**：
1. `AndroidManifest.xml` **未声明** `android:configChanges` → 旋转、深浅色切换、字体缩放都会**销毁重建 Activity**；
2. 重建后 `remember` 块重新执行，`new MutexGameStore(base, FileSaveMutex(...))` → 再次 `mutex.acquire()`；
3. 旧实例的 `FileLock` **从未释放**（全仓 `.release()` 只出现在 `FileSaveMutex` 内部与测试里，**没有任何 `onDispose`/`onStop` 调用点**）；
4. 同一进程内对同一文件二次 `tryLock()` 抛 `OverlappingFileLockException` → `acquire()` 返回 false；
5. `MutexGameStore.save()` 静默 `if (acquired)` 跳过 → **旋转一次之后，本局所有进度都不再落盘**，且**无任何提示**。

**实测证据**（探针，已删除）：
```
PROBE first acquire=true
PROBE second acquire (no release)=false   ← 模拟旋转
PROBE third acquire after release=true
```

**影响**：Android 用户横竖屏切换一次 → 后台杀进程 → 进度全丢。这是**数据丢失**，按 `sudoku-review.md` 属 P0/P1 边界。桌面端不受影响（窗口不重建）。

**修复建议**（二选一，推荐 ①）：
- ① **把 store 提升到 Activity 作用域**：`private val store by lazy { ... }`（或 `remember` 外、`onCreate` 里建一次），配 `onDestroy` 里 `if (isFinishing) mutex.release()`。这样重建不重复抢锁。
- ② 在 `MutexGameStore` 加 `close()`，`MainActivity` 用 `DisposableEffect { onDispose { ... } }` 释放——但 `onDispose` 在重建时也会触发，需保证"释放后再抢"的顺序，比 ① 脆弱。

**同时建议**：`MutexGameStore` 的只读降级**至少要给一次可见提示**（当前是完全静默），否则用户永远不知道自己在只读。

### P1-B · `Reveal`（看答案/认输）整条链路不可达

**位置**：`state/GameAction.kt:68` → `GameReducer.kt:79,241` → `Msg.Revealed` → `Strings.msgRevealed`

**事实**：`GameAction.Reveal` 在**生产代码中零派发点**。全仓 `Reveal` 的非测试引用只有定义与 reducer 分支本身；UI 里没有任何按钮/快捷键/菜单项派发它。

**但它的下游全部写好了**：
- `GameReducer.reveal()` 完整实现（填满答案、`revealed=true`、`settled=true`、`recordAbandon` 记一次放弃）；
- `GameViewModel.canResume` / `persist` 都判了 `!state.revealed`；
- `GameState` 有 `revealed` 字段、`Snapshot` 快照它也带了（保证撤销能回退）；
- `Strings` 中英都写了 `msgRevealed`；`I18nGuardTest` 还专门测它的渲染。

**判断**：这不是"预留设计"，是**功能做完了但忘记接线**。后果：玩家卡死时**没有任何"看答案/认输"出口**，只能硬重置（重置不计放弃、清零计时，等于免费重来，统计语义反而被绕过）。

**修复建议**：在顶栏或「游戏设置」抽屉加一项「看答案」（需二次确认，因为不可撤销地结束本局）。文案已就绪，只差一个 `onAction(GameAction.Reveal)`。

### P2-A · Reset 后再次通关不计入统计 —— 已实测复现

**位置**：`GameReducer.reset()`（`GameReducer.kt:259`）

**问题**：`reset()` 把 `won/settled/revealed/hintUsed/hintsCount/elapsed` 全部归零，**但没有重置 `outcomeCounted`**。而 `settle()` 的记账判据正是 `if (state.outcomeCounted) state.stats else recordWin(...)`。

**实测证据**（探针，已删除）：
```
PROBE 1st win:               won=true  gamesWon=1 counted=true
PROBE 2nd win after Reset:   won=true  gamesWon=1 counted=true   ← 应为 2
```

**影响**：通关 → 点重置 → 认真再解一次 → **第二次通关不进胜场统计**。同理 `abandonIfInProgress()` 在"重置后再开新局"时也会因 `outcomeCounted` 为 true 而漏记放弃。

**修复**：`reset()` 里补 `outcomeCounted = false`。一行。注意 `reset` 是 `pushUndo` 的，撤销回来时 `outcomeCounted` 不会被快照恢复（`Snapshot` 里没这个字段）——这正是它设计上"不随存档/快照"的取舍，所以 reset 必须显式清。

## 6. 附：值得保留的设计亮点（重构时勿丢）

- `SaveCodec` 的**逐字段宽松降级**（坏难度→Normal、缺行→默认、整体失败→null 不抛）：存档是外部输入，一个坏字段不该废掉整局。
- `FileGameStore`/`AndroidGameStore` 的 **tmp + ATOMIC_MOVE** 原子写，且同目录保证 move 原子性。
- `undoStack.takeLast(300)` + `redoStack` 双向截断（注释明确指出"只截一边会让栈无限增长"）。

### 7.1 P1-A · Android 旋转后存档静默变只读 ✅

**改法**：存档实例从 `remember { ... }`（Activity 作用域）提升为**进程级单例**
（`MainActivity.companion.sharedStore()`，`@Volatile` + 双重检查）。

**为什么这个改法而不是"加 onDispose 释放"**：文件锁在**同一 JVM 内共享**，`tryLock()` 不会等待、
直接抛 `OverlappingFileLockException`。因此只要抢锁发生两次，第二次必然失败——"释放后再抢"要保证
严格时序，在 Activity 重建路径上很脆弱。做成进程级后，**抢锁在整个进程生命周期只发生一次**，
重建只是复用同一实例。跨**进程**并发写仍由这把锁保护（那才是多实例的真实场景）；
进程退出由 OS 释放锁，无需显式 `release()`。

**验证**：探针实测——同一实例重复 `acquire()` 返回 `true`（可写），另建实例返回 `false`（只读，
即旧代码路径）。已确认 `AndroidGameStore` 只持有 `File`（不持有 Activity），`AppGlobals` 存的是
`applicationContext`，因此进程级单例**不泄漏 Activity**。
