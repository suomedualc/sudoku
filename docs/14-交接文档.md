## 1. 十分钟上手

### 1.1 这是什么

Kotlin Multiplatform + Compose Multiplatform 的**单机数独**，视觉"手写纸 + 简约油墨"（纸墨 / 夜墨两套主题）。
**无第三方 UI 组件库**——控件、图标、棋盘全部 `Canvas` 自绘。当前启用 **Desktop(JVM) + Android**，iOS/Web 未接。

### 1.2 三条命令（先跑，建立基线）

```powershell

# ① 测试 —— 必须加 --rerun-tasks，否则 UP-TO-DATE = 根本没跑
```

## 2. 架构：记住这 4 件事

### 2.1 三层单向依赖（最重要的不变量）

```
core/     纯算法：Sudoku（位掩码 + MRV 回溯出题/求解）· CellCursor（光标策略）
            ↑ 零平台依赖、零 UI、零 IO
state/    纯状态机：GameAction → GameReducer.reduce() → Reduction(state, Msg)
           GameState · GameStore/SaveCodec · GameViewModel（唯一桥）
            ↑ 零平台依赖（存档走"端口注入"而非 expect/actual）
ui/       theme（墨线令牌）· components（全自绘）· screens · i18n
            ↑ 仅通过 7 个 expect/actual 触达平台
platform/ androidMain / jvmMain：GameStore 实现 · 字体 · 安全区 · 返回键 · 语言
```

**红线**：`core/`、`state/` 不许 `android.*` / `java.io` / 平台 API；`state/` **规则层**禁 Compose。
> ℹ️ **唯一例外是 `GameViewModel`**（`state/GameViewModel.kt:3-6` 用 `compose.runtime` 的
> `mutableStateOf` / `derivedStateOf`）：它是状态容器，需要重组感知，属职责内需要。
> 该例外已于 2026-10-24 第三轮接手时写入 `AGENTS.md` 红线 2，理由与代价见 §9.2。

### 2.2 状态机的形状

```kotlin
data class Reduction(val state: GameState, val message: Msg? = null)
GameReducer.reduce(state, action, random): Reduction
```

**关键设计：提示是"事件"不是"状态"**。`message` 作为第二返回值 + `GameViewModel` 的 `Channel` 投递。
放进 `GameState` 会被 data class 等值比较**吞掉相同文案**（真实修过的缺陷）。

**`Msg` 是语义键不是文案**：`Msg.Conflict(value)`，渲染在 `ui/i18n/Strings.render(msg)`。单测断言语义。

### 2.3 `GameAction` 全集（**23** 个）

| 类别 | Action |
|---|---|
| 对局 | `NewGame` · `Reset` · `Reveal` · `Hint` · `Pause` · `Resume` |
| 输入 | `Digit(value, advance)` · `NoteDigit(value)` · `Select` · `Deselect` · `Move` · `FocusFirstEmpty` |
| 历史 | `Undo` · `Redo` |
| 偏好 | `ToggleNoteMode` · `ToggleStrict` · `ToggleShowNotes` · `ToggleHintCandidates` · `ToggleDarkMode` · `SetLanguage` |
| 其它 | `BindKey` · `SyncElapsed` · `Navigate` |

**`Digit` vs `NoteDigit`**：`Digit` 行为取决于全局 `noteMode`；`NoteDigit` **无视 `noteMode`**（双键盘点空心数字直记笔记）。reducer 内部走同一个 `place()`，靠 `forceNote` 区分。

## 3. 关键机制（改之前必读）

### 3.1 存档

**位置**：桌面 `~/.sudoku-ink/save.txt` · Android `filesDir/save.txt`
**格式 v2**：纯文本 `key=value`，无第三方序列化（所以 `commonTest` 能直接测）。
**兼容**：逐字段宽松降级——坏难度→Normal、缺行→默认、整体失败→`null` 而非抛异常。**存档是外部输入**。
**写盘**：`tmp + ATOMIC_MOVE`，同目录保证原子性（`AndroidGameStore.kt:35-43`）。

### 3.2 多实例写锁（极易踩）

`MutexGameStore(base, FileSaveMutex(saveFile))`——抢不到锁**降级只读**，`writable=false`，由 `App` 弹墨条告知。

> ⚠️ 文件锁在**同一 JVM 内是共享的**：第二个 `tryLock()` 不等待，直接 `OverlappingFileLockException`。
> **因此 Android 必须用进程级单例**（`MainActivity.companion.sharedStore()`，已实测 L63-84）。
> 建在 `remember`（Activity 作用域）→ **旋转一次就静默变只读，本局进度全不落盘**（P1-A，`docs/13` §7.1）。

### 3.3 计时

单调时钟 + 锚点并账，**不是"每秒 +1"**。长局不漂移；切后台/最小化精确停表。
`SyncElapsed(seconds)` 是心跳动作，**不能因此触发重算**。

### 3.4 性能约定

- `derivedStateOf` 缓存 conflicts / progress —— 心跳 250ms **不能**触发 81 格重算；
- `NumberPad` 的 `legalMask` / `remaining` 用 `remember` 缓存；
- **出题实测 <20ms**（Expert 最慢 17ms），`dispatch` 同步执行安全。

### 3.5 布局断点

```kotlin
gameLayout(width, height) = if (width > height && height < 480.dp) Landscape else Portrait
```

**高度上限 480dp 是关键**：只看"宽>高"时桌面 1180×900 会被判横屏，双栏压窄棋盘。
**横屏不留上下浮动条槽**：撤销/重做改挂棋盘左侧竖轨（`BarRail`）。实测 891×411dp 棋盘由 160dp 提升到 237dp。

### 3.6 双键盘（B1）

主键盘下方一排**空心数字**，点它直接记笔记。`showNotePad` 由 `GameScreen` 按纵向预算算，`NumberPad` 只认布尔值。
**极小屏（360×640）自动隐藏**，退回"先切笔记模式"。

## 4. 视觉与文案纪律

### 4.1 两条铁律

1. **不靠颜色区分状态**——夜墨主题下颜色翻转，字形/线型不翻。用线重、线型、字形（实心/空心）。
2. **只有纸墨两色 + 墨四级 alpha**——`Ink.Black/Grey/Light/Faint`。对比度实测写在 `Ink.kt` 注释里。

### 4.2 所有可见文字必须走 `Strings`

`ZhStrings` / `EnStrings` 各实现一遍。`I18nGuardTest` 用 JDK 反射逐键断言两语言非空白、占位符一致。
**但守卫查不出"声明了没人用"**——加 key 后自己 grep 确认有引用。

> ✅ 本轮全量扫描 `commonMain` 中文字面量：8 处命中**全部白名单**（`require` 异常消息 5、`AppLanguage.label` 2、注释 1），**0 处违规**。

### 4.3 触控目标 ≥48dp

`HitAreaTest` 守着数字键 / 悬浮面板键 / 紧凑条目 / 图标按钮。棋盘格不套用按钮标准（测试已注明）。

### 5.1 写测试的规矩

- 改 `core/` 补 `commonTest`；改 `state/` 行为补 `GameReducerTest` / `GameStoreTest`（固定种子）；

- **断言要能区分修复与缺陷**。反例：B1 笔记行测试最初"连按 7 次↓仍能开局"，但越界实现按 5 次绕回 0 也正常——**改成按 4 次才能区分**。

### 5.2 实机冒烟（本轮已修默认路径）

```powershell
.\gradlew.bat :composeApp:createDistributable --offline
powershell -NoProfile -ExecutionPolicy Bypass -File tools\smoke-e2e.ps1 -Flow menu
```

11 条流：`menu` / `exit` / `win` / `theme` / `bar` / `ux` / `keys` / `keymap` / `stats` / `lang` / `reveal`。
脚本会备份并恢复玩家存档，截图落 `%TEMP%`。

> ✅ **`-ExePath` 默认值已修为相对路径**（本轮）：原默认 `D:\LESSON\sudoku\...` 在仓库迁到 `X:\sudoku-main` 后失效，
> 而当时**所有文档示例都不带 `-ExePath`**——照抄即失败。现在用 `$PSScriptRoot` 推导，从任意目录均可调用。

> ⚠️ **DPI 前提**：脚本内置 `Set-DpiAware()`（PER_MONITOR_AWARE_V2）+ `Get-DpiScale` 换算。
> 漏掉它：PowerShell 默认 DPI 不感知，`GetWindowRect` 给虚拟坐标而 `CursorPos`/`CopyFromScreen` 用物理坐标
> → **表现为"顶栏图标消失、棋盘溢出"，极像 UI bug**。

> ⚠️ **已知脚本缺陷（都不属产品问题）**：
>
> | # | 现象 | 根因 | 规避 |
> |---|---|---|---|
> | 1 | 截图棋盘空白 | `Save-Shot` 无重绘同步，截在显影动画首帧（`RevealMs=160`） | 复跑；或截图前加 ≥250ms |
> | 2 | `-Flow all` 连跑 `FOREGROUND LOST` / 窗口 1244×… | `Pin()` 用 `SetWindowPos(HWND_TOPMOST)` 抢前台被系统交接 | **逐流单独起进程**，流间 sleep |
> | 3 | `bar` 流首个按键被当成"打开难度抽屉" | 同上，`Pin` 在 `Down`/`Enter` 之间打断焦点 | 单跑该流；看截图而非退出码 |
> | 4 | 截图左边缘约 10px 透出背景 | `CopyFromScreen` 抓窗口边框/阴影偏移 | **不影响 UI 判定**（本轮像素实测：纸色到 x=1758，内容宽度正确） |

> **判据**：DPI 150% 下 `Pin` 后应为 **1770×1350**；237×39 之类是残窗，**不可据此报 UI 缺陷**。

## 7. 坑（按踩坑成本排序）

### 7.1 会静默损坏数据

1. **Android 存档必须进程级单例**——建在 `remember` 会在旋转后静默只读（§3.2）。
2. **存档是外部输入**——`load()` 坏数据必须返回 `null`，不能抛（启动期抛 = 起不来）。
3. **`outcomeCounted` 不随 Snapshot 回滚**——`reset()` 必须显式清，否则"通关→重置→再赢"第二次不计胜场。

### 7.2 会"看起来做了其实没有"

4. **`GameAction.Reveal` 曾整条链路不可达**——reducer/文案/测试全写好，UI 没按钮派发。
   **加新 Action 后必须 grep 确认有 UI 派发点。**
5. **声明了没人用的 i18n key** ——`I18nGuardTest` 查不出，要自己 grep。
6. **布局预算**——加一行控件前先算纵向够不够（B1 改了三版）。

### 7.3 环境类

7. **JDK 25 让 Gradle 8.14.4 直接失败**，报错只有版本号。
8. **冒烟脚本 DPI**——症状酷似 UI bug（§5.2）。
9. **`UP-TO-DATE` 等于没跑**——`jvmTest` 首次全绿是假象，必须 `--rerun-tasks` 或读 XML 的 `tests=`。

## 9. 本轮新增 · 接手必读

### 9.1 两个"看起来像产品 bug、其实是工具/进程语义"的假警报

| 现象 | 错误结论 | 真相与判据 |
|---|---|---|
| `SudokuInk.exe` 启动后 8.4MB / 5 线程 / `MainWindowHandle=0` | "启动失败、无窗口" | jpackage **两级进程**：launcher 转发给真正 JVM 进程（**326.6MB / 77 线程 / 标题 `数独 Sudoku`**）。判据：`Get-Process -Name SudokuInk` 找 300MB 级那个 |
| 截图右半"空白"、两侧透出背景文字 | "严重 UI 布局缺陷" | 逐像素实测：纸色 `R247 G245 B240` 延伸到 **x=1758**（图宽 1770），内容宽度正确。透出仅 **x=0..9（约 10px）**，是 `CopyFromScreen` 的边框偏移 |

> **教训**：判 UI 缺陷前**必须先做像素级测量**。这两条我都先判错过，记下来防止重犯。

### 9.2 ✅ 已裁决并修复：`state/` 层 import 了 Compose（红线 #2）

| 项 | 内容 |
|---|---|
| 原红线 | `state/` 禁 Compose / 平台 API |
| 违例 | `state/GameViewModel.kt:3-6` → `androidx.compose.runtime.{derivedStateOf,getValue,mutableStateOf,setValue}` |
| 复现 | `Get-ChildItem composeApp\src\commonMain\kotlin\...\state -Recurse -Filter *.kt \| Select-String "^import androidx"` |

**影响评估（实测，未夸大）**：
- `state/` 其余 **8 个文件 0 违例**（`GameReducer`/`GameState`/`GameStore`/`GameAction`/`Msg`/`KeyMap`/`GameStats`/`Language` 全干净）；
- `compose.runtime` 是 KMP **公共**库（非平台专属）→ 编译、双端运行、单测均不受影响；
- `GameViewModel` **已被 commonTest 覆盖**（`GameStoreTest` 28 处引用、`GameClockTest` 1 处），可测性未受损。

**裁决：方案① 改规则**（用户 2026-10-24 拍板）。理由与代价：

| 对比 | ① 改规则（**已采用**） | ② 改代码（未采用） |

| 代码改动 | 0 行 | ~20 行 + 2 个新文件 + `App.kt` 13 处调用点 |
| 测试改动 | 0 项 | `GameStoreTest` 28 处 + `GameClockTest` 1 处 |
| 耗时 | ~15 分钟 | 2–4 小时 |
| 风险 | 极低 | **中**：手工复刻 `derivedStateOf` 缓存语义若退化成"每次访问都重算"，心跳 250ms × 81 格会掉帧，**而 168 项测试查不出** |

选①的核心理由：`GameViewModel` 的职责就是"持有状态 + 通知观察者"，观察者机制是职责内需要；`compose.runtime` 跨平台可用，**不阻碍 iOS/Web 接入**。规则层（`GameReducer` 等 8 个文件）本来也确实是零依赖的——脏的是容器层，把它写清楚比大改更符合原意。

## 10. 一句话总结

> 三层单向依赖、`core`/`state` 零平台依赖、提示走事件不走状态、
> 不靠颜色靠字形与线重、改完必须跑全量（jvmTest 161 + Android 独有 7 = 去重 168）、
> 修缺陷必须配能反向验证的回归测试、
> **Android 存档实例绝不能建在会被重建的作用域里**。
>
> 三条元经验：
> **规则要放在 agent 能自动加载的位置**（`.codebuddy/` 写了等于没写）；
> **结论要能反向证伪**——`UP-TO-DATE` 等于没跑、截图不等于 UI 正确、`Measure-Object -Line` 会少计；
> **判 UI 缺陷前先做像素测量、判进程失败前先找真正的窗口进程**。
